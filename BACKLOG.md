# Backlog

Real, finishable improvements — the daily agent picks ONE and ships it end-to-end.
Rules: check items off when done, add follow-ups you discover, never do two at once,
smallest reviewable change wins.

**Safety:** Mort is a real, well-tested language. The daily agent works only on
**verifiable, low-risk surface** — new `std` modules, docs, examples, and tests —
and runs the relevant tests before pushing (`pip install ziglang`, then a targeted
`pytest` and/or `python mortc.py --run` on a small program). It does **not** change
the compiler internals (`mort/parser.py`, `mort/typechecker.py`, `mort/codegen.py`)
autonomously; those need careful human review with the full suite.

## Larger (sketch in the item before shipping — may need human review)
- [ ] Typechecker/codegen mismatch: `[]const u8 == []const u8` (and slice equality generally) passes `_check_expr`'s `==`/`!=` handling in `mort/typechecker.py` (slices aren't in `self.structs`, so the "cannot compare aggregate values" check doesn't catch them) but fails to compile in the C backend — `gcc` rejects the generated `struct mort_slice_const_u8 == struct mort_slice_const_u8` with "invalid operands to binary ==". Confirmed 2026-08-24 with a standalone repro (`slice(...) == slice(...)`) while building `examples/word_frequency.mx`. Practical impact: any `Map<[]const u8, V>` or `Vec<[]const u8>.index_of`/`contains` is silently broken for slice-typed keys/elements — not a typechecker error pointing at the problem, but a late C-backend compile failure. Two independent fixes are possible and need a human call: (a) typechecker rejects `==`/`!=` on slice types with a clear error (matching the existing aggregate-comparison rejection), or (b) codegen lowers slice `==` to a `memcmp`-based content comparison (which would change `Map`/`Vec.index_of` semantics for slice keys from "not currently usable" to "compares by content", a real behavior addition). Compiler-internals territory (`mort/typechecker.py` and/or `mort/codegen.py`), so left for human review rather than fixed autonomously.
- [ ] Resource-aware container API: `Vec.get` returns an aliasing copy (unsafe for resource elements) and `Vec.destroy` frees only the backing array. Design a safe `get_ref` returning `*T` and an element-dropping destroy without breaking the plain-`T` API. Note (found while writing `docs/stdlib.md` 2026-08-02): `std.map`'s `Map.get` and `Map.insert`'s overwrite-of-an-existing-key path have the identical aliasing-copy / no-drop gap for a resource `Value` — worth folding into the same design rather than a separate pass. Update 2026-08-09: `std.map.remove` (shipped today) closes this gap for the delete-a-key path specifically — it moves the value out cleanly, no aliasing/no-drop issue there — but `get`/`set`/insert-overwrite are unchanged and still need the `get_ref`/dropping-`destroy` design.
- [x] `std.random.below(random, maximum)` uses `next_u64(random) % maximum`, which is not uniformly unbiased when `maximum` doesn't evenly divide 2^64 (modulo bias, more pronounced for large `maximum`). Shipped 2026-08-05: `std/random.mx` gained a module header doc comment (it previously had none) documenting the xorshift64 PRNG, its non-cryptographic/deterministic-from-seed nature with a pointer to `std.crypto.random_fill` for security-sensitive use, and the modulo-bias caveat on `below`/`between` with guidance that it's negligible for small `maximum` and to avoid this module where a formally uniform distribution over a large range is required. Comment-only change (no functional/behavioral change), so no version bump; verified via existing `test_portable_random_and_byte_slice_modules` (`python -m pytest -q tests/test_mort.py -k random`, 3 passed) and a fresh `python mortc.py --run` of a small program importing `std.random` (exit 0), plus full suite (338 tests) green. An unbiased rejection-sampling variant remains a possible follow-up if a caller ever needs uniformity guarantees — no evidence of demand yet.
