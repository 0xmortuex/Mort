# Backlog

Real, finishable improvements — the daily agent picks ONE and ships it end-to-end.
Rules: check items off when done, add follow-ups you discover, never do two at once,
smallest reviewable change wins.

**Safety:** Mort is a real, well-tested language. The daily agent works only on
**verifiable, low-risk surface** — new `std` modules, docs, examples, and tests —
and runs the relevant tests before pushing (`pip install ziglang`, then a targeted
`pytest` and/or `python mortc.py --run` on a small program). It does **not** change
the compiler internals (`mort/parser.py`, `mort/typechecker.py`, `mort/codegen.py`)
autonomously; those need careful human review with the full suite.

## Larger (sketch in the item before shipping — may need human review)
- [ ] Typechecker quirk: a literal-vs-literal integer expression like `0 - 1` is constant-folded and range-checked against the *statically-inferred* type at the point it appears, even inside a generic `fn<T>` body where the containing branch is unreachable for that particular `T` instantiation (confirmed 2026-09-07 writing `std.math.sign<T>`: `return 0 - 1;` in the `value < 0` branch fails to compile when `T` is instantiated as `u64`, even though `value < 0` is always `false` for an unsigned `value` so the branch never executes). A literal-vs-*variable* expression (`let zero: T = 0; let one: T = 1; return zero - one;`) does not hit this — no constant folding happens, so it type-checks and compiles fine for both signed and unsigned `T`, with the unsigned case simply never reaching that branch at runtime. Worked around in `sign<T>` by using the variable form. Not a correctness bug (rejecting `-1` for `u64` is right where it's actually reachable), but the *unreachable-branch* case is a real ergonomic trap for anyone writing a similar generic signed/unsigned helper — worth a human look at whether dead-branch literal range-checking should be relaxed, or at minimum documented. Compiler-internals territory (`mort/typechecker.py`'s constant-folding/range-check path), so left for human review rather than fixed autonomously.
- [ ] Typechecker restriction: `_writes_through_raw_pointer` in `mort/typechecker.py` (the exemption from the "cannot overwrite a resource binding" check) only recognizes assignment through a raw pointer (`ptr[i]` / `*ptr`), not through a slice (`[]T` indexing). Confirmed 2026-08-31 while building `std.vec.slice_reverse`: `value[index] = value[other]` on a `[]Res` slice (`Res` a `resource struct`) is rejected at compile time even though the identical pattern through `Vec`'s raw-pointer-backed storage (`(*value).data[i] = (*value).data[j]`) compiles fine via `Vec.swap`. Practical impact: any slice-based in-place algorithm over resource elements (a `slice_reverse`, a slice-based sort, a partition step) is unusable for resource `T`, even though the underlying operation (move-through-a-temporary, never aliasing) is exactly as safe as the `Vec`-based equivalent — the checker's exemption just doesn't recognize the access pattern. Fix would extend `_writes_through_raw_pointer` (or a parallel check) to also recognize `Index` targets whose object is a (non-const) slice type, mirroring the existing raw-pointer case. Compiler-internals territory (`mort/typechecker.py`), so left for human review rather than fixed autonomously.
- [ ] Typechecker/codegen mismatch: `[]const u8 == []const u8` (and slice equality generally) passes `_check_expr`'s `==`/`!=` handling in `mort/typechecker.py` (slices aren't in `self.structs`, so the "cannot compare aggregate values" check doesn't catch them) but fails to compile in the C backend — `gcc` rejects the generated `struct mort_slice_const_u8 == struct mort_slice_const_u8` with "invalid operands to binary ==". Confirmed 2026-08-24 with a standalone repro (`slice(...) == slice(...)`) while building `examples/word_frequency.mx`. Practical impact: any `Map<[]const u8, V>` or `Vec<[]const u8>.index_of`/`contains` is silently broken for slice-typed keys/elements — not a typechecker error pointing at the problem, but a late C-backend compile failure. Two independent fixes are possible and need a human call: (a) typechecker rejects `==`/`!=` on slice types with a clear error (matching the existing aggregate-comparison rejection), or (b) codegen lowers slice `==` to a `memcmp`-based content comparison (which would change `Map`/`Vec.index_of` semantics for slice keys from "not currently usable" to "compares by content", a real behavior addition). Compiler-internals territory (`mort/typechecker.py` and/or `mort/codegen.py`), so left for human review rather than fixed autonomously.
